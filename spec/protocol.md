# Widget protocol v2

The contract between the chat widget (`@ticketping/chat-widget` 2.x) and `ticketping-backend`. The widget, the backend and the docs are all built against this file. Changes go through a PR that updates this file first.

Status: **draft for review** (milestone M1). Nothing here is implemented yet.

Related: `token-test-vectors.json` (generated by `reference/generate-vectors.ts`), `reference/verify-token.ts` (executable version of section 5), `../docs/REBUILD_PLAN.md`.

---

## 1. Conventions

| Topic                 | Rule                                                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| API origin            | `https://api.ticketping.com`. All widget REST paths start with `/api/v2/widget/`                                              |
| Socket                | `wss://api.ticketping.com/ws/v2/widget/`                                                                                      |
| Encoding              | JSON, UTF-8. Request and response bodies are objects, never bare arrays                                                       |
| Field names           | `camelCase` in JSON. The backend maps to its own names                                                                        |
| IDs                   | Opaque strings (the backend's short UUID `sid`s). Clients never parse them                                                    |
| Time                  | ISO 8601 UTC with milliseconds, e.g. `2027-01-01T09:30:00.000Z`                                                               |
| Client header         | Every REST request sends `X-Ticketping-Client: widget/<version> (<integration>)`, e.g. `widget/2.0.0 (react)`                 |
| CORS                  | Widget endpoints answer CORS for any origin; the origin rules in 2.3 decide whether the request is served                     |
| Forward compatibility | Clients ignore unknown fields, unknown event types and unknown `event.type` values. The server ignores unknown request fields |
| Breaking changes      | New path prefix (`/api/v3/`) and socket path. Additive changes need no version bump                                           |

### 1.1 Errors

Every non-2xx REST response, and every socket error frame, carries:

```json
{
  "error": {
    "code": "origin_not_allowed",
    "message": "Human-readable, English, safe to log.",
    "details": {}
  }
}
```

`code` is stable and machine-readable; `message` can change. `details` is optional. Widely used codes:

| HTTP | Code                         | Meaning                                                                        |
| ---- | ---------------------------- | ------------------------------------------------------------------------------ |
| 400  | `invalid_request`            | Body failed validation. `details.fields` maps field to reason                  |
| 401  | `key_invalid`                | Publishable key unknown, revoked, or malformed                                 |
| 401  | `credentials_invalid`        | Visitor or access token unknown, expired or revoked. Client re-boots (2.4)     |
| 403  | `origin_not_allowed`         | Request from an origin that isn't allowed (2.3)                                |
| 403  | `verified_identity_required` | Config requires a signed token for this action                                 |
| 403  | `identified_only`            | Config only serves identified users; anonymous actions refused                 |
| 404  | `not_found`                  | Resource doesn't exist **or** isn't visible to this caller (never distinguish) |
| 413  | `payload_too_large`          | Upload or body over the limit                                                  |
| 429  | `rate_limited`               | `Retry-After` header (seconds) is always set                                   |
| 5xx  | `server_error`               | Retry with backoff                                                             |

## 2. Credentials

### 2.1 Overview

| Credential          | Format                                        | Lifetime                       | Stored by widget         | Grants                                                |
| ------------------- | --------------------------------------------- | ------------------------------ | ------------------------ | ----------------------------------------------------- |
| Publishable key     | `pk_` + 24 base62 chars                       | Until rotated in the dashboard | No (it's in the snippet) | Selects one widget config                             |
| Visitor token       | `tpv_` + 43 base64url chars (32 random bytes) | 12 months since last use       | `localStorage`           | Acts as one anonymous visitor of one widget config    |
| Access token        | `tpa_` + 43 base64url chars                   | 15 minutes                     | `localStorage`           | Acts as a verified customer (plus their visitor)      |
| Refresh token       | `tpr_` + 43 base64url chars                   | 30 days, rotates on every use  | `localStorage`           | Gets a new access + refresh pair                      |
| Host identity token | JWT, HS256 (section 5)                        | At most 10 minutes; single use | Never                    | Proves to Ticketping who the host's logged-in user is |
| Identity secret     | `tpis_...`, shown once in the dashboard       | Until rotated                  | Never (host server only) | Signs host identity tokens                            |

There is one publishable key per widget and one identity secret per team. A developer needs exactly two values: the key in the snippet, and `TICKETPING_IDENTITY_SECRET` on their server, used the same way in local development, staging and production.

The server stores only SHA-256 hashes of visitor, access and refresh tokens. Identity secrets are stored as-is, because HMAC verification needs them.

### 2.2 Local development

- `http://localhost`, `http://127.0.0.1` and `http://[::1]`, on any port, are always accepted, so the snippet works locally with no setup. A config can switch this off ("Allow localhost").
- Conversations started from those origins are flagged `isTest`: TEST badge in the dashboard, `[TEST]` prefix in Slack (same routing as real ones), excluded from reports, deleted after 30 days, and listed only on local origins, so they never show up in a real user's history.
- A team can also mark an allowed domain as a test domain (e.g. `staging.acme.com`), with the same effect.

### 2.3 Origin rules

- The server reads the `Origin` header on `boot`, `identify` and the socket handshake. A request without `Origin` is refused.
- Apart from the local origins above, the origin must be `https://`. Its host must equal an allowed domain exactly, or match a `*.acme.com` wildcard (which matches subdomains, not `acme.com` itself).
- **Learn-then-lock:** while a config's domains are unlocked, any `https://` origin is accepted and recorded. The dashboard lists recorded origins as one-click "allow" suggestions and nudges the team to lock before go-live. Once locked, unlisted origins get `403 origin_not_allowed`, and the attempt still shows up as a suggestion.
- This is defense in depth. Non-browser clients can forge `Origin` (including to look local, which only gets their conversations flagged as test). What protects data is that history requires a verified identity (section 5) and anonymous data is bound to the visitor token.

### 2.4 Which credential a request carries

REST requests send exactly one bearer credential in `Authorization: Bearer <token>`:

- the **access token**, if the visitor is verified and holds one;
- otherwise the **visitor token**.

`boot` is the exception: it carries the publishable key and the (optional) visitor token in its body, because it's the call that creates them.

On `401 credentials_invalid`, the widget follows one path: if it has a refresh token, refresh (6.6); if that fails, or it had none, discard stored credentials and `boot` again as a new anonymous visitor, and emit an `error` event (`code: "session_lost"`).

### 2.5 Browser storage

Keys are namespaced by publishable key so two widgets on one site don't collide:

| Key                           | Value                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| `tp:<publishableKey>:visitor` | `{ "token": "tpv_...", "visitorId": "..." }`                                         |
| `tp:<publishableKey>:session` | `{ "accessToken", "accessExpiresAt", "refreshToken", "refreshExpiresAt", "userId" }` |

Cookies are not used: from a customer's site, a cookie on `api.ticketping.com` is third-party and is blocked or partitioned by Safari and Chrome. With `consent: 'pending'`, nothing is read or written until consent is granted; `consent('denied')` deletes both keys.

## 3. Objects

### 3.1 `WidgetConfig` (returned by `boot`)

```json
{
  "id": "wc_8s7d6f",
  "isTest": false,
  "team": {
    "name": "Acme",
    "avatars": ["https://.../a.png"],
    "replyTimeHint": "Usually replies within a few hours"
  },
  "appearance": {
    "accentColor": "#7BC043",
    "colorMode": "auto",
    "position": "bottom-right",
    "launcher": { "icon": "chat", "label": null }
  },
  "texts": {
    "greetingTitle": "Hi there",
    "greetingBody": "Ask us anything. We reply here and by email.",
    "composerPlaceholder": "Write a message..."
  },
  "features": { "ai": true, "attachments": true, "emailCapture": true },
  "security": { "requireVerifiedIdentity": false, "identifiedOnly": false, "loginUrl": null },
  "branding": { "poweredBy": true },
  "socket": { "url": "wss://api.ticketping.com/ws/v2/widget/", "heartbeatSeconds": 25 }
}
```

`isTest` is `true` when this page's origin is a local or test origin (2.2); the widget then shows a small "Test" tag. `texts` holds only the English catalog at launch. Keys the dashboard doesn't override fall back to the widget's built-in catalog. `branding.poweredBy` is always `true` except on Enterprise plans.

### 3.2 `Identity`

```json
{
  "state": "verified",
  "userId": "user_123",
  "name": "Ada",
  "email": "ada@acme.com",
  "contactEmail": null
}
```

| `state`      | Meaning                                                                                                                            |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `anonymous`  | No identify call yet. `contactEmail` may be set by the inline email form                                                           |
| `unverified` | Host called `identify()` without a token. Profile shown to agents with an "Unverified" badge; no history beyond this visitor's own |
| `verified`   | A host identity token was accepted. History across devices                                                                         |

### 3.3 `Conversation`

```json
{
  "id": "cs_2k3j4h",
  "createdAt": "...",
  "updatedAt": "...",
  "phase": "team",
  "isTest": false,
  "unreadCount": 1,
  "assignee": { "name": "Grace", "avatarUrl": "https://..." },
  "ticket": {
    "id": "tk_9d8f7g",
    "status": { "slug": "waiting-for-customer", "label": "Waiting for customer", "theme": "BLUE" }
  },
  "lastMessage": { "...": "Message (3.4)" }
}
```

| `phase`         | Meaning                                                         | Widget shows                                   |
| --------------- | --------------------------------------------------------------- | ---------------------------------------------- |
| `ai`            | The AI agent is answering                                       | AI label on replies, "Talk to a person" button |
| `needs_contact` | Handed off, but the team can't reach an anonymous visitor yet   | Inline email form                              |
| `team`          | A ticket exists and people answer (from Slack or the dashboard) | Ticket status, agent names                     |

A conversation exists only once the visitor has sent a message (no empty conversations). `ticket.status` is one of the team's own statuses (`TicketStatus`), so the widget renders `label` and `theme` instead of hard-coding status names. `theme` is one of `RED`, `GREEN`, `BLUE`, `YELLOW`, `NEUTRAL`.

### 3.4 `Message`

```json
{
  "id": "cm_5g6h7j",
  "conversationId": "cs_2k3j4h",
  "clientId": "6f0c2f3e-6f2a-4b8e-9a51-1c2d3e4f5a6b",
  "createdAt": "...",
  "sender": { "type": "AGENT", "name": "Grace", "avatarUrl": "https://..." },
  "kind": "message",
  "body": { "format": "markdown", "content": "Fixed, try again?" },
  "attachments": [],
  "event": null
}
```

| Field         | Rules                                                                                                                                                                                                                                                                                                                  |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sender.type` | `USER` (the visitor), `AGENT` (a person on the team), `AI`, `SYSTEM`                                                                                                                                                                                                                                                   |
| `clientId`    | Present only on the visitor's own messages: the ID the widget generated (6.3)                                                                                                                                                                                                                                          |
| `kind`        | `message` (render a bubble) or `event` (render a divider or inline UI from `event`)                                                                                                                                                                                                                                    |
| `body.format` | `text` (visitor messages; render as text with links detected), `markdown` (agents and AI; safe subset: emphasis, links, lists, code, quotes), `html` (email replies only; sanitized by the server with an allowlist and sanitized **again** by the widget with DOMPurify). Unknown formats: render `body.fallbackText` |
| `event`       | Set when `kind` is `event`: `{ "type": "handoff" }`, `{ "type": "contact_requested" }`, `{ "type": "contact_saved" }`, `{ "type": "ticket_created", "ticketId": "..." }`, `{ "type": "status_changed", "status": {...} }`                                                                                              |

### 3.5 `Attachment`

```json
{
  "id": "ca_1q2w3e",
  "name": "screenshot.png",
  "size": 48213,
  "contentType": "image/png",
  "isImage": true,
  "url": "https://...",
  "urlExpiresAt": "..."
}
```

`url` is a signed download URL valid for 1 hour. It's re-issued whenever the message is fetched again. Only `image/png`, `image/jpeg`, `image/gif` and `image/webp` have `isImage: true` and may be shown inline. Everything else, including SVG and HTML, is served with `Content-Disposition: attachment`.

## 4. REST endpoints

### 4.1 `POST /api/v2/widget/boot`

The first call on every page load (after consent). It's idempotent.

Request:

```json
{
  "publishableKey": "pk_...",
  "visitorToken": "tpv_... or omitted",
  "page": { "url": "https://app.acme.com/billing", "title": "Billing", "referrer": "" },
  "locale": "en-GB",
  "client": { "version": "2.0.0", "integration": "react" }
}
```

Response `200`:

```json
{
  "config": { "...": "WidgetConfig (3.1)" },
  "visitor": { "id": "vi_7h6g5f", "token": "tpv_... (only when a new token was issued)" },
  "identity": { "...": "Identity (3.2)" },
  "conversations": ["...Conversation (3.3), newest first, up to 20"],
  "unreadCount": 0
}
```

- A missing, unknown or other-config visitor token gets a fresh anonymous visitor, never an error. The widget must store `visitor.token` whenever it's present.
- If the request carries no access token, `identity` describes the visitor as anonymous or unverified. Verified state is restored by the widget using its stored session (6.6), not by `boot`.
- The server records `client.version`, `client.integration` and the origin for the dashboard install check, and pushes "widget detected" to the team's notification socket.
- Errors: `401 key_invalid`, `403 origin_not_allowed`, `429 rate_limited`.

### 4.2 `POST /api/v2/widget/identify`

Auth: visitor token. Body is one of:

```json
{ "token": "<host identity JWT>" }
```

```json
{
  "profile": {
    "email": "ada@acme.com",
    "name": "Ada",
    "company": { "id": "acme" },
    "attributes": { "plan": "pro" }
  }
}
```

**Signed (`token`)**, verified as in section 5:

1. Find or create the customer by `(team, externalId = sub)`. Never match by email or a null ID.
2. Update the customer's profile from the signed claims. Signed claims always beat unsigned ones.
3. If this visitor is already linked to a **different** customer, refuse with `409 visitor_bound_to_other_user`. The widget handles user switches itself (6.5), so this only fires on misuse.
4. Link the visitor to the customer, and attach this visitor's own anonymous conversations to the customer. No other conversations are merged.
5. Issue a session.

Response `200`:

```json
{
  "identity": { "...": "Identity, state verified" },
  "session": {
    "accessToken": "tpa_...",
    "accessExpiresAt": "...",
    "refreshToken": "tpr_...",
    "refreshExpiresAt": "..."
  },
  "conversations": ["...all of the customer's conversations, newest first, up to 20"],
  "unreadCount": 2
}
```

Errors: `400 token_invalid` with `details: { "reason": "<code from 5.3>", "claim": "exp" }` and a plain-language `message`, e.g. "exp is 24h after iat; the maximum is 10 minutes". Also `409 visitor_bound_to_other_user`.

**Unsigned (`profile`):** stores the profile on the visitor and sets identity to `unverified`. It returns `{ identity }`. It never grants history, never creates or matches a customer by email, and is refused with `403 verified_identity_required` when the config requires verified identity.

History scope: a verified customer sees their conversations from every widget config of the team. Test conversations (2.2) are listed only on local and test origins.

### 4.3 `POST /api/v2/widget/visitor/contact`

Auth: visitor or access token. Body `{ "email": "ada@acme.com" }`. Saves the email the team will use to notify an anonymous visitor of replies; it doesn't change `identity.state`. Moves any conversation in `needs_contact` to `team`, which creates its ticket. The server adds a `contact_saved` event message. Response `200 { "identity": {...} }`.

### 4.4 `GET /api/v2/widget/conversations?before=<cursor>&limit=20`

Auth: visitor or access token. Response `{ "conversations": [...], "nextCursor": "..." | null }`, newest first. An anonymous or unverified caller sees only this visitor's conversations; a verified caller sees the customer's (4.2).

### 4.5 `GET /api/v2/widget/conversations/{id}/messages?before=<messageId>&limit=50`

Auth: visitor or access token. Response `{ "messages": [...], "hasMore": true }`. Messages come oldest first within the page, and `before` pages backwards. A conversation the caller can't see returns `404 not_found`.

### 4.6 `POST /api/v2/widget/uploads`

Auth: visitor or access token. `multipart/form-data` with one `file` field. Response `201 { "attachment": {...} }`. The ID is then referenced in `message.send`. Limits: 10 MB per file, 5 files per message; types are images, PDF, plain text, CSV, and common office documents. The server checks the size, and checks the content type by sniffing the file, not trusting the header. Uploads not referenced by a message within 24 hours are deleted.

### 4.7 `POST /api/v2/widget/session/refresh`

No `Authorization` header. Body `{ "refreshToken": "tpr_..." }`. Response `200 { "session": {...} }` with a new access **and** refresh token; the old refresh token stops working.

- Reusing a refresh token **within 30 seconds** of its rotation returns `409 refresh_token_rotated`: another tab already rotated it, so the widget re-reads storage (6.6).
- Reusing it **later** is treated as theft: the whole token family is revoked and the response is `401 credentials_invalid`.

### 4.8 `POST /api/v2/widget/session/logout`

Auth: access token. Body `{ "refreshToken": "tpr_..." }`. Revokes the session family. Response `204`. The widget then deletes its stored visitor and session and boots as a fresh anonymous visitor (the old visitor stays linked to the customer, so their history isn't exposed to the next person on the device).

## 5. Host identity tokens

The host's server signs a short-lived JWT for its logged-in user; the widget gets it through `getToken()` and passes it to `identify`. There's no SDK: any JWT library works, and `token-test-vectors.json` is the conformance suite for the backend and for every docs snippet.

### 5.1 Format

The smallest valid token is `{ "sub": "<user id>", "exp": <now + 300> }` signed with HS256, which is one line in any JWT library:

```js
jwt.sign(
  { sub: user.id, email: user.email, name: user.name },
  process.env.TICKETPING_IDENTITY_SECRET,
  { expiresIn: '5m' }
)
```

```python
jwt.encode({"sub": str(user.id), "email": user.email, "exp": int(time.time()) + 300}, settings.TICKETPING_IDENTITY_SECRET, algorithm="HS256")
```

| Claim        | Required | Rule                                                                                                                       |
| ------------ | -------- | -------------------------------------------------------------------------------------------------------------------------- |
| `sub`        | Yes      | The host's user ID, as a string, 1 to 255 characters, not just whitespace. Stringify numeric IDs                           |
| `exp`        | Yes      | NumericDate (seconds, not milliseconds), at most **10 minutes** from now                                                   |
| `iat`, `nbf` | No       | NumericDate. Checked when present (libraries often add `iat`)                                                              |
| `aud`        | No       | When present, `"ticketping"` or an array containing it                                                                     |
| `email`      | No       | Valid email, at most 254 characters                                                                                        |
| `name`       | No       | String, at most 255 characters                                                                                             |
| `company`    | No       | `{ "id": string (1 to 255), "name"?: string }`                                                                             |
| `attributes` | No       | Flat object, at most 50 keys matching `^[A-Za-z_][A-Za-z0-9_]{0,63}$`; values string (up to 1024), number, boolean or null |

Other claims and headers (`jti`, `kid`, `iss`, `role`, ...) are ignored, never trusted. The whole token must be at most 4096 bytes.

### 5.2 Secrets

- One identity secret per team, used in every environment. HMAC key = the UTF-8 bytes of the secret string exactly as shown (no base64 decoding).
- **Rotation without downtime:** "Rotate" creates a new secret and keeps the old one working for 24 hours (or until "Revoke old secret now"). The server tries the active secrets, newest first; there are never more than two, so no `kid` is needed.
- Revoking a secret takes effect immediately.

### 5.3 Verification order

Checks run in this order and the **first** failure is the result, so every implementation returns the same code for the same token:

| #   | Check                                                                    | Error `reason`                                   |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| 1   | Size at most 4096 bytes                                                  | `token_too_large`                                |
| 2   | Three base64url segments; header and payload decode to JSON objects      | `token_malformed`                                |
| 3   | `alg` is exactly `HS256` (rejects `none`, `HS512`, `RS256`, ...)         | `alg_not_allowed`                                |
| 4   | Signature matches an active secret (constant-time compare)               | `signature_invalid`                              |
| 5   | `sub`, then `exp`: present, then type                                    | `claim_missing` / `claim_invalid` (with `claim`) |
| 6   | `aud` if present; `iat` (and `exp > iat`) and `nbf` types                | `audience_invalid` / `claim_invalid`             |
| 7   | `email`, `name`, `company`, `attributes` format                          | `claim_invalid` (with `claim`)                   |
| 8   | `iat` and `nbf` not more than 60 s in the future                         | `token_not_yet_valid`                            |
| 9   | `now < exp + 60`                                                         | `token_expired`                                  |
| 10  | `exp <= now + 600 + 60`                                                  | `lifetime_too_long`                              |
| 11  | Not used before: SHA-256 of the signature segment, kept until `exp + 60` | `token_replayed`                                 |

The leeway is 60 seconds of clock skew. Single use needs nothing from the host: the server keys its replay cache (per team, Redis `SET NX` with expiry) on the token's signature, and records it only after every other check has passed. The widget always calls `getToken()` for a fresh token, so hosts must not cache tokens.

### 5.4 Test vectors

`token-test-vectors.json` contains `now` (the clock to use), the team's secrets, and cases of `{ name, token, seen?, expect }`, where `seen` lists replay keys already in the cache. An implementation conforms when, for every case, it gives `expect`: either `{ valid: true, claims }` with the normalized profile, or `{ valid: false, error, claim? }`. The vectors are generated (`npm run spec:vectors`), so CI fails if the generator and the committed file drift apart.

## 6. Socket

### 6.1 Connection and auth

1. Connect to `config.socket.url`. The URL carries no credentials; the server checks `Origin` as in 2.3.
2. Within **5 seconds**, send the first frame:

```json
{
  "v": 1,
  "type": "auth",
  "data": {
    "publishableKey": "pk_...",
    "visitorToken": "tpv_...",
    "accessToken": "tpa_... (if verified)",
    "resumeFrom": "<cursor or omitted>"
  }
}
```

3. The server replies `auth.ok` `{ "visitorId", "identity", "cursor" }`, or closes with a code from 6.7.

Only one auth frame is accepted per connection. Before `auth.ok`, every other frame closes the socket with `4000`.

### 6.2 Frames

Every frame is `{ "v": 1, "type": "<name>", "id"?: "<client frame id>", "data": { ... } }`. The server echoes `id` on direct replies (`ack`, `error`). Server events that can be replayed carry `cursor`.

**Client to server**

| Type                   | `data`                                                                                     | Notes                                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| `auth`                 | see 6.1                                                                                    | First frame only                                                                         |
| `auth.refresh`         | `{ "accessToken" }`                                                                        | Swap in a new access token without reconnecting (6.6)                                    |
| `ping`                 | `{}`                                                                                       | Every `heartbeatSeconds`                                                                 |
| `message.send`         | `{ "clientId", "conversationId": "... or null", "body": { "text" }, "attachmentIds": [] }` | `conversationId: null` starts a new conversation. Text 1 to 10,000 characters            |
| `conversation.handoff` | `{ "conversationId" }`                                                                     | "Talk to a person"                                                                       |
| `conversation.read`    | `{ "conversationId", "upToMessageId" }`                                                    | Clears unread up to and including that message                                           |
| `typing`               | `{ "conversationId", "isTyping" }`                                                         | At most one per 2 seconds; the server ignores extras                                     |
| `visitor.context`      | `{ "page": { "url", "title" }, "attributes"?: {...} }`                                     | SPA navigation and `update()`. Attributes are refused when verified identity is required |

**Server to client**

| Type                   | `data`                                                           | Notes                                                                                   |
| ---------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `auth.ok`              | `{ "visitorId", "identity", "cursor" }`                          |                                                                                         |
| `pong`                 | `{}`                                                             |                                                                                         |
| `ack`                  | `{ "clientId", "message", "conversation"? }`                     | Reply to `message.send`. `conversation` is present when one was just created            |
| `error`                | `{ "error": { "code", "message" }, "clientId"? }`                | Reply to a failed frame (e.g. `rate_limited`, `not_found`, `invalid_request`)           |
| `message.created`      | `{ "message" }` + `cursor`                                       | Any new message in a visible conversation, including the visitor's own from another tab |
| `conversation.updated` | `{ "conversation" }` + `cursor`                                  | Phase, ticket status, assignee or unread changed                                        |
| `typing`               | `{ "conversationId", "sender": { "type", "name" }, "isTyping" }` | Treat as `false` after 6 s without an update                                            |
| `unread.updated`       | `{ "total" }`                                                    | Total across conversations, for the launcher badge                                      |
| `sync.reset`           | `{}`                                                             | Resume isn't possible; refetch with REST (4.4, 4.5)                                     |

### 6.3 Sending messages

- The widget generates `clientId` (UUID v4), shows the message as **sending**, and keeps it in an outgoing queue that survives reconnects (not page reloads).
- The server de-duplicates on `(visitor, clientId)` for 24 hours. Re-sending after a reconnect is always safe and returns the same `ack`.
- `ack` means stored. The widget marks the message **sent** and replaces it with `ack.message`. If no `ack` arrives within 10 seconds, it retries on the next connection; after 3 failed attempts, it marks the message **failed** with a "Retry" action.

### 6.4 Resume

The widget remembers the latest `cursor` it saw (from `auth.ok` and replayable events). On reconnect it sends it as `resumeFrom`. The server then replays, in order, every `message.created` after the cursor and one `conversation.updated` per conversation changed since. If the cursor is older than 24 hours or more than 200 events behind, the server sends `sync.reset` instead.

### 6.5 Identity changes on an open socket

- After a successful `identify` (REST), the widget sends nothing on the socket; it **reconnects** with the new access token so the server re-subscribes it to the customer's conversations.
- On a user switch (`identify` with a different `userId`), the widget logs out (4.8), deletes stored state, boots a fresh visitor, then identifies.
- Logout or identity changes in another tab arrive through the `storage` event; the widget follows them.

### 6.6 Session refresh

- The widget refreshes about 60 seconds before `accessExpiresAt`, inside `navigator.locks.request('tp:<publishableKey>:refresh')`, so only one tab refreshes. The other tabs pick up the new tokens from the `storage` event.
- On `409 refresh_token_rotated`, the widget re-reads storage and uses whatever another tab stored.
- After refreshing, it sends `auth.refresh` on the open socket. If the access token expires without one, the server closes with `4011`.
- If refresh fails with `401`, the widget calls `getToken()` again and re-identifies. If that also fails, it falls back to anonymous (2.4) and emits `error`.

### 6.7 Heartbeat, close codes, reconnect

The client pings every `heartbeatSeconds` (25 seconds by default). With no `pong` within 10 seconds, it reconnects. The server closes connections that send nothing for 60 seconds.

| Code           | Meaning                                       | Client action                                      |
| -------------- | --------------------------------------------- | -------------------------------------------------- |
| `1000`, `1001` | Normal close / server going away              | Reconnect with backoff                             |
| `4000`         | Protocol error (bad frame, frame before auth) | Reconnect once; if repeated, stop and emit `error` |
| `4001`         | Auth not received within 5 seconds            | Reconnect                                          |
| `4003`         | Key invalid or origin not allowed             | Stop. Emit `error`                                 |
| `4004`         | Visitor or access token invalid               | Recover as in 2.4, then reconnect                  |
| `4011`         | Access token expired                          | Refresh (6.6), then reconnect                      |
| `4029`         | Rate limited                                  | Reconnect after at least 30 seconds                |
| `4100`         | Server restart                                | Reconnect now, with up to 2 seconds of jitter      |

Backoff: 0.5 s, 1 s, 2 s, 4 s ... up to 30 s, each with full jitter. Backoff resets after a connection has been up for 60 seconds. While the page is hidden, the widget doesn't reconnect until it becomes visible again, unless a message is in the outgoing queue.

## 7. Conversation flow

```
visitor sends first message
  ├─ config.features.ai = true  -> phase "ai": AI replies (sender AI)
  │     └─ AI decides to transfer, or visitor sends conversation.handoff
  │           └─ "handoff" event message
  └─ AI off -> straight to handoff

handoff
  ├─ visitor is verified, unverified with email, or has contactEmail
  │     -> ticket created -> phase "team" -> "ticket_created" event, Slack post
  └─ anonymous without email
        -> phase "needs_contact" -> "contact_requested" event -> inline email form
        -> POST visitor/contact -> ticket created -> phase "team"

phase "team"
  agent replies from Slack or dashboard -> message.created (sender AGENT)
  status changes -> conversation.updated + "status_changed" event
```

- AI replies are produced off the request path; the visitor sees `typing` from `{ type: "AI" }` meanwhile.
- `identifiedOnly` configs refuse `message.send` from anonymous visitors with `identified_only`. The widget shows a "Log in to chat" button linking to `security.loginUrl` instead of the composer.
- Slack: the widget config's channel, else the team's first connected channel, else no Slack post. Test conversations are prefixed `[TEST]`.

## 8. Limits

| What                   | Limit                                                                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `boot`                 | 30 per minute per IP and key                                                                                                        |
| `identify`             | 10 per minute per visitor                                                                                                           |
| `message.send`         | 20 per minute and 300 per hour per visitor                                                                                          |
| Uploads                | 10 per minute per visitor; 10 MB per file; 5 per message                                                                            |
| New anonymous visitors | 60 per hour per IP per config; beyond that, Cloudflare Turnstile is required (a future extension; returns `429 challenge_required`) |
| Message text           | 10,000 characters                                                                                                                   |
| Socket connections     | 5 per visitor (one per tab); the oldest is closed with `1000` beyond that                                                           |

## 9. Reserved for v2.x

These aren't in v2.0. The names are reserved so v2.0 clients ignore them safely:

- `message.delta` for streamed AI replies, plus `body.citations`.
- `body.format: "blocks"` for interactive messages (buttons, forms), always with `fallbackText`.
- Event types `csat_requested` and `csat_submitted`.
- `/api/v2/widget/help/*` for the help space.
